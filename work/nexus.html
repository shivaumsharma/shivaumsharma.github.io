Case study · Graph engine · Backend

Nexus

A dependency-graph engine that answers one question for an organisation or a supply chain: if this fails, what else breaks, and what should I fix first?

Role
Designed and built the engine and API
Context
Started as my BHEL internship project (May to Jun 2025)
Stack
Python (standard library core), FastAPI, PostgreSQL, SQLAlchemy 2.0, Alembic, Docker
Scale
141 tests in the repo, 100+ at BHEL

The problem

Large organisations and industrial supply chains are webs of dependencies: applications, services, vendors, raw materials, projects. When one node fails, the blast radius is rarely obvious, and the nodes that matter most are often the ones nobody ranks.

The task was to model those dependencies as a graph, simulate failures, and rank single points of failure in a way that experts would recognise as sensible.

What I built

A directed weighted graph and its algorithms (BFS, DFS, Dijkstra, max-flow and min-cut, cycle detection, topological sort, Tarjan's strongly connected components), written from scratch on the standard library, with a documented complexity table.

On top of it: cascading and compound failure simulation, risk analysis that ranks single points of failure by blast radius (optionally weighted by disruption likelihood), and mitigation recommendations with projected risk reduction. A FastAPI service exposes it with JWT auth and viewer, analyst and admin roles.

Decisions that mattered

  1. Keep the domain layer free of frameworks

    The graph and algorithms import neither FastAPI nor SQLAlchemy. That makes them testable in isolation with no database, so the algorithm tests run in well under a second, and reusable outside a web API.

  2. Write the algorithms myself, then measure them

    Owning the code meant I could find the bottleneck in it: an O(E²) step that took 40 seconds on 10K to 50K node graphs. Fixing it brought the run to 0.1 seconds, a 400× speedup.

  3. Check the output against people who know the domain

    Criticality scores reached 94% alignment with domain-expert rankings across 12+ projects, and the work was approved by BHEL IT leadership.

  4. Secure by default

    There is no default JWT secret or demo admin account. The first registered user bootstraps as admin, everyone after starts as viewer.

Results

  • 400×faster on 10K to 50K node graphs (40s to 0.1s)
  • 94%alignment with domain-expert criticality rankings
  • 12+projects it was applied across at BHEL
  • 141tests in the open-source repo

The 400× figure compares the fixed engine against my own earlier implementation, not against a third-party graph library.

What went wrong, and what is next

  • Reviewing the repo as an outside visitor would turned up a broken Docker quickstart and insecure defaults for the JWT secret and demo admin. I fixed both, and added real-world BHEL scenario tests kept separate from the main suite.
