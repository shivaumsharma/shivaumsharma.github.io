Case study · Fraud detection · Graph ML

Argus

An AI risk manager for promo and referral abuse, built for the Razorpay AI Buildathon 2026. It treats fraud as a graph problem, because the signal only exists across rows.

Role
Designed and built the pipeline, evaluation and dashboard
When
Razorpay AI Buildathon 2026, Track 02 (AI Risk Manager)
Stack
Python, NetworkX, Louvain community detection, Streamlit, an LLM for write-ups only
Guardrail
No code path bans, blocks or moves money; a human takes every action

The problem

Fraud detection usually scores one row at a time. That approach cannot catch a promo or referral abuse ring however good the model is, because a farmed account seen alone is designed to look ordinary. Thirteen "different" signups behind one device only look suspicious together.

Any system that flags people also has to be explainable and auditable, which is what the RBI's FREE-AI framework asks of AI used in fraud detection.

What I built

Accounts become graph nodes, linked wherever they share a device, payment instrument, IP subnet or referral chain. Deterministic clustering runs first (hard-signal connected components, then Louvain over the full graph), then behavioural scoring, then an explicit rules stage that hunts for evidence a cluster is legitimate: real households, hostels and organic referral trees.

Only after those four stages does an LLM write a plain-English case for a human analyst, bounded to HOLD_BONUS, MANUAL_REVIEW or NO_ACTION. It never decides whether a cluster is suspicious.

Decisions that mattered

  1. Let the LLM write, never decide

    Every flag traces to a specific graph edge and feature score decided by deterministic stages, so it can be explained and audited.

  2. Actively look for innocence

    Households, hostels and office networks are also dense clusters. A dedicated stage looks for spread-out activity, varied order values and ongoing engagement to suppress the flag.

  3. Freeze the test, then report it once

    The synthetic holdout was generated from a fresh seed and run a single time, with ring sizes re-grounded in measured fraud cluster sizes from real datasets. I did not iterate on it after seeing results.

  4. Try to break it, and test on real data

    I ran the unmodified clustering on real labelled data, on real botnet traffic, and against an attacker who deliberately restructures the graph.

Results

  • 100%hard-signal ring recall (40 of 40)
  • 85%soft-signal ring recall (34 of 40)
  • 98.7%cluster-level precision
  • 2.5%false positives on planted look-alike households

Those four figures are on a synthetic cohort of 7,500 accounts. On real labelled data the same clustering reached 99.2% precision on YelpChi and a 7.3× lift on the Elliptic Bitcoin graph. Against graph-fragmentation evasion, recall held at 100% down to 2-member pods.

What went wrong, and what is next

  • On real botnet traffic (CTU-13) the clustering was very precise but caught few hosts: 100% precision with 21.4% recall. The FRAUDAR baseline recalled more (57.1%) at only 11.4% precision. That is a real precision and recall tradeoff, and I reported it as one.
  • A fairness audit found a small recall gap by city tier, but it traces to a single miss among only 9 Tier-1 rings, too few to conclude anything, so I reported it as inconclusive rather than smoothing it over. The headline numbers are synthetic, and the real-data results are node-level, not ring-level.
